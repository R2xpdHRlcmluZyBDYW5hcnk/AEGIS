# 并行处理与一致性边界

## Go 控制台

`backend` 提供 Go HTTP、事件库、规则管理与事件桥接实现。每个服务默认 `GOMAXPROCS` 不超过 4，`IPS_CPU_WORKERS` 可进一步缩小解析池；部署保留管理员的 CPU 亲和性，并为控制台服务配置最多四核的 CPU 时间配额。Go 调度器和有界工作池允许 JSON 解析、事件规范化、原文压缩和规则策略处理同时使用多个核心。

入库采用单写者与 WAL；只有事件事务提交成功后才发布读取游标。桥接将完整行分成有界批次，并行解析后按来源顺序写出，文件及目录同步完成后提交检查点。独立 SQL 使用共享上限为三个的辅助连接，协调写入锁固定同一个读快照；前台请求最多四个，概览保留一个名额。未取得辅助名额时使用自己的只读连接，不再创建线程池。

网络统计使用单独后台读取通道，最近事件使用有容量上限的内存 SQLite。成功的网络结果受总字节预算与 32 个条目限制，刷新失败保留原结果；无成功结果时显示准备状态。原始文件补查有单独名额，最多扫描末尾 200 MiB；两遍有界扫描得到精确总数和分页，避免内存随分页偏移增长。前台切换条件或断开连接会取消对应计算。SSE 在长查询期间发送心跳，不用固定的连接时限反复中断查询。

默认总览等待常驻池的读取快照，缓存刷新占锁时不会改用磁盘统计；等待可被客户端取消。常驻池每批优先合并新提交事件，再用剩余预算预热历史，历史预热不阻止实时追赶。桥接与检测守护共用日志布局：持久布局读取日志根目录下的 `snort` 子目录，旧布局读取 `/var/log/snort`；来源目录不存在时启动失败，不发布空闲成功状态。

内存事件库由一个独立存活连接持有，另外最多一个连接用于串行刷新和查询。取消请求后，查询连接可以被连接池丢弃与替换，表结构和已有记录不会随它销毁；新连接重新设置内存临时存储和查询函数。来源暂时读取失败时保留可用快照并标记更新延迟，恢复后清除提示；仅内存缓存损坏或缺失时自动重建并从持久事件库重新预热。健康接口记录缓存重建次数及不含查询内容的 SQLite 错误码，磁盘数据库和历史游标不受重建影响。生命周期回归覆盖反复取消查询、缓存表结构缺失、来源故障恢复和容量回收。

历史入库每次事务最多处理 1000 行。积压超过 8 MiB 时，每轮先处理事件流末尾最多 256 KiB 的完整记录，再推进历史批次；前者只写事件，不推进持久历史游标。历史仍逐行补齐，交叠记录通过原有事件摘要去重，重启可安全重放。健康接口分别报告历史与最近事件的字节积压，以及常驻池实际时间范围；读取或规范化失败会反映为入库错误。

规则源同时最多处理两个来源，上游解析器分享四核预算，Go 策略解析复用有界工作池。候选生成与目录解析可并行；配置锁、规则冲突合并、校验、热重载、检查点和最终替换保持有序。规则事务持有跨进程配置锁直至提交或回滚结束，失败时保留未应用编辑。状态发布独立于引擎采样和规则操作，不要求 HTTP 请求打开引擎套接字。

Go 兼容性测试覆盖精确大整数、字段查询、MITRE 原文匹配、网络统计与安全事件分组；生命周期测试覆盖登录与来源校验、批量编辑回滚、失败配置校验、UTF-8 日志分页及稀疏日志恢复。运行 `python -B build_tools/go_backend.py -- test -race -count=1 ./...` 验证竞态。下面保留 Python 对照实现及检测维护工具的并行说明，Go 服务不加载其 Web 处理模块。

## Python 对照与检测维护工具

控制台、规则管理器和数据桥使用分配给控制面的 CPU。子进程继承服务的 CPU 亲和性，不改变 Snort 检测进程、队列或引擎实现。计算并行采用标准库的 spawn 进程池，不在已有多线程服务中 fork。

## 模块与任务

| 路径 | 并行方式 | 顺序边界 |
| --- | --- | --- |
| `parallel_cpu.py` | 每个服务复用最多 4 个计算进程，所有调用共享有界提交名额 | 每条流水线最多挂起与进程数相同的批次，按输入顺序返回 |
| `parallel_sql.py` | 查询线程加最多 3 个共享辅助线程，各自拥有只读连接 | 同一业务查询固定 WAL 读快照；不共享连接跨线程执行 SQL |
| 概览、事件、告警分组 | 计数、分页和独立聚合 SQL 并发执行 | 计数、排行和列表使用同一快照，原始事件类型与去重口径保持一致 |
| 网络快照刷新 | 单个独立后台读线程，聚合 SQL 在同一只读事务内顺序执行 | 不借用前台 SQL 辅助线程，筛选缓存隔离，保留刷新间隔、退避和取消 |
| 数据桥 | 完整行分块后并行解析 JSON、识别类型及编码输出 | 单写者有序提交；输出文件及目录同步完成后，原子更新并同步检查点 |
| 事件入库 | 并行规范化、计算事件摘要及压缩原文 | 解析整批成功后才更新内存与读取位置，SQLite 保留单写者 |
| 历史投影补齐 | 批量并行计算关联标识 | 派生库事务和游标提交顺序不变，后台仍按工作占空比让出资源 |
| 文本规则目录与内置目录解析 | 较大输入分块解析，复用服务计算池 | 先规范化续行，再分完整规则，保留文件、记录及重复签名顺序 |
| Python 事件适配器的规则评级元数据 | 大型评级目录分批并行解析，缓存重建互斥 | 按文件和规则顺序合并，保留优先级与最后出现的规则；不修改 Snort 引擎 |
| Python 查询条件与 ATT&CK 原文匹配 | 完整候选行批量交给计算进程 | 保留布尔条件、分页、精确整数、扫描限制和取消；原本完整下推的元数据查询仍完整检索，支持调用方取消 |
| 原始日志与内存兼容查询 | 批量解析和过滤并行 | 保留原有条数、扫描范围、顺序与分页；日志句柄由协调线程关闭 |
| 多规则源更新 | 最多两个来源任务并发，按总进程预算限制各自解析器 | 来源结果按固定顺序合并；共享来源索引加锁，冲突失败不替换生效规则 |
| PulledPork3 | 保留现有下载、流式提取和分块多进程解析 | 上游身份、校验、重复规则优先级和补丁版本继续验证 |

目录控制、连接生命周期、单条记录的操作、SQLite 提交、检查点推进、规则冲突合并与最终文件替换是协调步骤。浏览器 DOM 更新遵循浏览器主线程约束。单条 SQLite 语句内部仍由 SQLite 执行，并行安排在独立 SQL 和候选行处理层，不能仅因线程数增加而声称一条 SQL 平均占用四核。

## 资源与调度

前台默认允许 4 个读取请求，其中概览保留一个名额，其余用于日志；预取、网络快照与历史补齐继续独立调度。SQL 辅助线程由服务共享，不随请求无限创建。当辅助线程已占用或写入锁繁忙时，当前查询仍可用独立只读连接完成，不等待写入锁。辅助连接初始化成功后才释放快照协调锁；投影提交也参与相应的协调。

实时连接在计算前和刷新等待期间检查客户端断线，关闭或快速翻页时及时释放有界连接名额；等待检查不发起额外查询。连接上限维持不变。

网络快照单次后台计算默认没有执行时长上限，服务关闭或数据库世代变化仍会取消计算。启动时预热一次默认范围，之后只刷新最近 60 秒内访问过的范围，正常每 30 秒刷新。失败以 5 秒起步退避，最长 60 秒。每次计算后的后台刷新与重试共同等待至少三倍于本次线程 CPU 时间的冷却期，持续刷新约占单核的四分之一。新访问范围的首次计算可以提前进行，仍逐个计算。会话排序只处理有身份的记录，旧版无身份连接摘要直接逐条计入。

只更新 Web 专用模块且无其他服务资源变更时，部署器仅替换变化模块并重启 ips-web；校验失败同样仅回滚控制台。未变化的配置和服务资源文件不重写，检测引擎、日志桥和规则管理器保持运行。

同一范围和筛选条件的成功网络快照在刷新失败或超过新鲜期限后仍保留，响应包含原更新时间和更新状态，不以零或空图替代。缓存仍受字节预算和条目数约束；清空历史或数据库世代变化立即使旧快照失效。冷启动、缓存淘汰或新筛选条件没有成功快照时显示准备状态或真实错误，不借用其他条件的数据。

页面读取缓存按完整查询、时间参数和分页键隔离；最多保留 15 分钟的成功结果供内部后台刷新使用。交互式 HTTP 查询等待新结果，计算未完成时 REST 返回 HTTP 202，SSE 发送心跳；相同参数重连复用有界后台任务，默认没有查询执行时限。后台刷新合并、队列和失败重试间隔均有界，失败结果不覆盖成功缓存。参数变更、清空历史和写操作会使相应缓存失效；入库故障仍从实时写入状态返回。初次查询的语法及数据库错误正常报告。任务生命周期与资源边界见 [部署说明](../README-deploy.md#长查询与缓存)。

概览统计常驻内存事件池中的全部事件，默认时间范围由池内明细的实际覆盖范围决定。同一时间戳的记录按事件编号确定先后，容量边界上的记录也参与概览统计。点击图表或指标后用池内明细执行同一套 SQL 筛选和聚合，清除筛选后返回概览快照。安全事件、威胁狩猎和阻断日志默认及重置范围为 1 小时，保留时间选择及分页。请求区间完整落在池内覆盖范围时读内存，部分或全部超出时整段查询磁盘库。

进程启动时由独立线程从磁盘分批预热最新事件，先发布已经读入的事件概览，再扩大覆盖范围。其他页面的后台预取在预热完成后开始。新事件成功入库后尝试合并到常驻池；池正被查询占用时跳过同步合并，由独立刷新线程按磁盘游标追赶。预算用满时由新事件替换最旧事件。池内明细不因页面关闭、空闲时间、磁盘自动回收而释放，显式清空历史同时清空事件池。进程退出后在下次启动时重新预热。

系统状态显示概览网络统计等核心组件健康；磁盘统计索引和历史网络统计保留在接口诊断数据中。概览状态使用默认快照及其时间范围，历史网络统计在查询历史范围时计算。健康检查的 `overview_ready` 表示已有可用的默认概览快照。

网络统计没有完整快照时，后台工作线程先缓存同一时间范围的连接数、DNS 与 TLS 计数及日志地址榜，再以同一组会话代表记录计算端点地址数、应用、协议和载荷字节统计，避免为端点数额外扫描和排序一次。会话最大包数、字节数及时间使用分组聚合，代表记录和应用归属保留原有排序语义。后续阶段尚未完成时继续提供已经算出的结果，已有完整快照时优先保留完整结果。各阶段共用取消条件和后台工作预算。

`tests/benchmark_network_summary.py --baseline <可信的旧版 overview_metrics.py> --source-db <开发电脑上的数据库副本> --repeats 7 --html <源码外报告路径>` 可复现汇总路径对照；省略数据库参数时生成合成会话。前后逐次比较完整结果并交错计时，报告记录输入时间范围、实现摘要、原始计时和中位数。计时不含设备传输、HTTP 和浏览器渲染，不能作为检测吞吐量结论。

部署时可通过 `deploy.ps1 -UpdateBackend -PreloadMemoryMiB 512` 设置常驻事件表及其索引的固定预算，允许 1 至 1024 MiB。显式固定值优先于旧的内存比例和上限设置，按实际事件逐步占用。入库事件缓冲上限为该预算的四分之一，共享响应缓存上限为八分之一，均单独计入进程内存。查询工作内存、工作进程及其他服务内存另计。未设置固定值时沿用内存比例和上限计算事件池预算。

开发机可运行 `python -B tests/benchmark_first_pages.py --baseline <提交>`，使用同一份合成数据库对照冷首屏、重复读取和持续入库下的进程 CPU 时间。该基准使用真实 HTTP 与 SSE 入口，独立引擎状态采样和网络聚合不计入其 CPU 窗口。

浏览器实时流短暂断开时立即尝试一次 REST 读取，持续断开期间定期补读；短暂恢复不显示连接失败。持续失联保留最近结果并报告，收到成功数据后恢复显示。查询替换时取消旧请求、订阅和重连提示计时器，旧响应不能覆盖新条件。

概览的地址排行按全部日志出现次数统计；连接应用、传输协议和连接源按真实会话身份去重，生命周期快照不重复累计连接或流量。DNS、TLS、事件类型和检测签名筛选扩展到具有相同引擎会话身份的日志，IP 与协议继续直接约束，独立筛选维度可以跨记录匹配同一会话。DNS 与后续 TCP 连接不因时间或地址相近而合并。没有会话身份的旧记录仅在本身为连接摘要时计入连接，保留原始日志。

派生网络投影格式为 3，补充会话身份和双向包数；升级时由原有有界后台补齐任务重建派生数据，不重写事件库。滚动时间范围在快照计算时解析，避免将每次请求的时间戳变成新的缓存键。

计算进程数由 CPU 亲和性和 `IPS_CPU_WORKERS` 限制，最多为 4。较小输入直接执行，避免进程间复制和调度开销；索引规则策略保留已有直接执行路径，大文本扫描使用有界进程。多来源更新限制嵌套的 PulledPork3 解析预算，并保留 `IPS_PULLEDPORK_WORKERS` 的更低上限。单个来源仍可使用完整解析预算。

数据桥每轮读取总量有界，各输入文件轮转调度；有余量时继续处理尚有积压的文件。记录长度、文件数量和稀疏区域恢复仍有限制。服务的 CPU 配额支持四核计算，内存上限为 256 MiB。规则管理器任务上限为 64，以容纳受限的 RPC 线程、来源任务和计算子进程。

入库发现积压后及时处理下一批；超过 8 MiB 时，历史统计补齐、事件池历史预热和日志后台预取让出磁盘资源，前台查询继续执行。三个日志页的后台首屏范围与界面默认值一致，均为 1 小时。入库按最多 1000 条提交，写连接页缓存上限为 64 MiB，保留 WAL 与 FULL 同步。

事件流读取位置与最后一批事件在同一事务提交，重启校验文件身份及位置之前的内容摘要后继续读取，未完成的行保留到下一次。旧库首次升级没有读取位置时，顺序寻找最后已存原文的首次出现位置，再继续处理；找不到原文时从文件开头幂等补录，避免固定回读长度跳过积压或迟到事件。该首次定位可能需要读取较长的历史文件，后续重启直接使用持久位置。

空闲和写入错误使用较低频率重试。写入失败保持待提交数据和读取位置，不继续吞入新的无界积压。CPU 池发生工作进程故障后，失败的批次向调用方报错，下一次任务重新创建工作池。服务停止时取消排队任务、打断 SQL 并等待工作进程回收。

CPU 任务等待共享提交名额时也检查调用方取消，取得名额后提交前再次检查；取消者只释放自己取得的名额。已经运行的计算不会被强行终止，仍由原工作进程完成并归还名额。等待结果用 `Future.exception(timeout)` 判断是否完成，再通过 `result()` 传播任务异常，避免把工作函数抛出的 `TimeoutError` 当成轮询超时无限重试。回归覆盖满队列取消、读取输入期间取消、工作函数超时，以及后续任务继续可用。

2026-11-07（Australia/Perth，UTC+08:00）查询 [Python concurrent.futures 官方文档](https://docs.python.org/3/library/concurrent.futures.html)，条件为 `Future.result`、`Future.exception` 与 `TimeoutError` 的等待和异常传播语义。结果：`result()` 会重新抛出工作函数的异常，`exception()` 返回工作函数的异常对象；两者等待未完成任务时都可能产生等待超时。因此不能仅凭异常类型判断任务仍在运行。查询前复用本文的进程池与取消约定，新增合成工作进程回归验证这一边界。

## 恢复与验证

数据桥不在空闲轮询中反复同步文件和重写检查点。磁盘写入或工作进程失败时，检查点保持在上一次已持久化的位置；重启可重放原生日志。崩溃可能留下重复的完整记录，事件库使用既有事件身份去重。输出尾部未完成的行在有界范围内截断并从源日志重放，完整原生日志保持不变。超出恢复边界时停止并保留证据。

后端部署备份并校验程序、配置及独立的并行资源覆盖文件；启动失败时回滚。资源覆盖只涉及数据桥与规则管理器，不更新检测服务。部署使用 `deploy.ps1 -UpdateBackend`，并按需要显式设置 `-WebReadWorkers 4`。

`tests/test_parallel_runtime.py`、`tests/test_bridge_recovery.py` 验证实际工作进程、并行 SQL、固定快照、取消、工作池恢复、故障重放和串行结果一致性。`tests/check_multicore.py` 仅在开发电脑临时目录生成合成数据，比较单工作单元和四工作单元的完整输出摘要及实际耗时；可用 `--html <源码外路径>` 导出包含代码和完整输出的独立报告。报告不代表路由器性能，也不承诺所有小任务提速。
