# 签名策略与生效边界

签名管理区分待应用编辑与已应用配置。保存编辑后点击“应用更改”，才会提交签名来源、手动签名、封禁、禁用、动作和抑制策略。应用过程备份文件，校验 Snort 配置并确认热重载代次；失败恢复原配置并保留待应用编辑。

告警抑制按 GID 与 SID 生成 Snort `suppress` 表。整组策略保存分组身份，每次生成时从当前引擎及签名来源目录展开成员，不保存永久固定的成员列表。引擎升级后，同一分组新增的签名也需要进入生成表。已经入库的历史事件不会因后来设置抑制而删除。

内置目录缓存包含引擎文件身份、配置和禁用文件的变更信息。后台核对已应用策略与引擎的指纹；检测到变化后，通过独立事务重新生成派生配置、执行 Snort 校验和热重载，保留待应用编辑。控制台启动或退出维护后等待一分钟再检查，失败后至少等待五分钟重试，避免与部署或前台操作争用。只有 root 对端能主动调用 `refresh-policies` 提前同步。该同步不下载签名来源，也不提交待应用编辑。

回归测试覆盖内置目录变化、新增签名的整组抑制、内置签名禁用、文本签名禁用、强制阻断、拒绝、动作覆盖、手动签名、封禁和签名来源离线应用。生成动作与抑制表的测试使用合成签名，真实设备只执行实际部署所需的配置校验和轻量健康检查。
